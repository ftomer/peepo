# Contributing to Peepo

Peepo is a hidden object game for children aged 3-12.
Contributions are welcome from anyone: new levels, bug fixes, features, translations, docs and tooling.

Everyone whose work is merged is credited in [CONTRIBUTORS.md](CONTRIBUTORS.md).
If you would rather be credited under a different name or handle, say so in your pull request.

## Setting up

Peepo is a plain Flutter app.
There is no game engine and no backend.

```bash
flutter --version   # 3.35.6 or newer, Dart 3.9.2 or newer
flutter pub get
flutter test        # unit and widget tests
flutter run         # device or simulator
flutter run -d macos
```

Building for a physical iOS device also needs your own signing identity:

```bash
cp ios/Flutter/Signing.example.xcconfig ios/Flutter/Signing.xcconfig
# then put your Apple Developer Team ID in it
```

`Signing.xcconfig` is gitignored, because a signing identity belongs to whoever is building rather than to the repository.
The simulator, macOS and web need no team at all, and the project opens without the file.

The scene pipeline in `tools/` is Python and needs its own virtualenv:

```bash
python3 -m venv .venv
.venv/bin/pip install -r tools/requirements.txt
```

## Rules that are not negotiable

Peepo is enrolled in the App Store Kids Category and is rated 4+, so COPPA and App Review guidelines 1.3 and 5.1.4 apply.
A pull request that breaks any of the following will not be merged, however good the rest of it is.

- **No network.** The app never opens a socket. No analytics, no crash reporting, no ads, no accounts, no remote config.
- **No dependency that phones home.** Adding a package to `pubspec.yaml` means arguing in the pull request that it cannot reach the network. `audioplayers` pulls `http` in transitively for the URL sources it also offers; the game only ever builds `AssetSource`. Keep it that way.
- **No third-party content with a licence attached.** Every image is generated by the art pipeline in `tools/` and every sound by `tools/audio.sh`. Do not add stock art, stock audio, or a font you did not check.
- **A parental gate in front of anything that leaves the app.** External links and anything resembling a purchase sit behind one.

See [docs/kids-direction.md](docs/kids-direction.md) for the reasoning.

## Code

Match the surrounding code.
The lint set is `flutter_lints`; `flutter analyze` must be clean before you open the pull request.

- Tests live in `test/`, one file per unit, and new behaviour needs one.
- Difficulty is derived, not authored. Art and scene metadata are made for the Look band (5-7); `lib/models/difficulty.dart` derives Peek, Seek and Hunt from it. Do not hand-tune a level per band.
- Do not edit iOS or Android version values by hand. `pubspec.yaml` is the single source of truth, see [Versioning](#versioning).
- Never edit files marked auto-generated.

## Adding a level

This is the most valuable kind of contribution and the most involved one.
Read the Scene pipeline section of [README.md](README.md) first, then [docs/scene-pipeline.md](docs/scene-pipeline.md) and [docs/scene-meta.md](docs/scene-meta.md).

A level needs, in one pull request:

1. A room brief and prop prompts, following [docs/imgenprompts/art-direction.md](docs/imgenprompts/art-direction.md).
2. Generated source art under `rawimages/<level>/`, produced by `tools/generate_art.py`. See [Source art](#source-art) below, because `rawimages/` is not in the repository.
3. A build recipe at `tools/scenes/<level>.build.json` and metadata at `tools/scenes/<level>.meta.json`.
4. The baked output under `assets/levels/<level>/`, produced by `tools/scene.sh build`. Do not hand-place anything; rerun the tool.
5. An entry in `assets/levels/levels.json`, in play order, with its find list and `maxObjects` ceiling.
6. The two asset lines in `pubspec.yaml`. `tools/scene.sh build` adds them.
7. A music prompt line in `tools/audio_prompts.json` and one run of `tools/audio.sh music <id>`. `test/audio_test.dart` fails without it.
8. A dense variant, if the level should be harder for the 8-10 and 11-12 bands.

Music comes from Lyria 3 through the Gemini API and sound effects are synthesized, both by `tools/audio.sh`.
Model-written music carries no copyright claim and may ship commercially, which is exactly why it is used.
Running the art and audio tools needs your own Gemini API key in `.env` as `GEMINI_API_KEY`; copy `.env.example` to start.
That file is gitignored and must stay that way.

### Source art

`rawimages/` holds the generated plates and sprite sheets that levels are baked from.
It is roughly 160 MB, so it is not tracked in git; it is published as a `rawimages` asset on the [Releases page](https://github.com/ftomer/peepo/releases).

You only need it to re-bake an existing level.
Running the game, changing code and adding a brand new level do not need it, because a new level generates its own art locally.

```bash
curl -L -o rawimages.tar.gz <url of the rawimages asset from Releases>
tar -xzf rawimages.tar.gz
```

## Translations

The app has no localization layer yet, so the first translation contribution is really two: adding `flutter_localizations` and extracting the strings, then the language itself.
Open an issue before starting that one so the approach can be agreed first.

## Versioning

`pubspec.yaml` holds `version: <major>.<minor>.<patch>+<build>`.
Bump it in the same commit as the change that earns it:

- **major** - breaking change to saved data or the scene JSON format, or a redesign that makes old levels unplayable.
- **minor** - new level, new screen, new gameplay feature, or a visible behaviour change.
- **patch** - bug fix, art or copy tweak, refactor, test or tooling change.

Bump the trailing build number on every version bump.

## Pull requests

- Branch off `main`.
- One concern per pull request.
- Commit messages: imperative subject, under 50 characters, body only when the "why" is not obvious. Do not add an AI agent as a co-author.
- Say in the description what you did and how you checked it. A level or a UI change wants a screenshot; a gameplay change wants a note on which age bands you played it in.
- `flutter analyze` and `flutter test` must pass. CI runs both.

Bug reports are most useful with the child's age band, the level, and what happened versus what you expected.
